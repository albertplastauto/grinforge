# Производительность: замеры, модель стоимости, план оптимизаций

## 1. Реперные замеры на целевой машине

RTX 4060 Ti 8 GB (8188 MiB), драйвер 617.14 (CUDA UMD 13.4), Windows 11 Pro 26200,
Ryzen 7 1800X, 32 GB RAM. Замеры 8 октября 2026, пул `grin.2miners.com:3030`, C32.

| Майнер | Версия | GPS | VRAM | Питание | Шары за 4.5 мин | Dev fee |
|---|---|---|---|---|---|---|
| GMiner | 3.44 | **0.07** | 7759 / 8188 MiB | 46–53 Вт | **0** | **5 %** |
| lolMiner | 1.98a | **не стартует** | — | — | — | 2 % |

Дословно из лога GMiner:

```
GPU0 PALIT NVIDIA GeForce RTX 4060 Ti 8GB: Selected 11GB Solver
DevFee:             5 %
Fidelity: 0.00
```

GMiner выбрал на 8-гигабайтной карте солвер, рассчитанный на 11 ГБ. Отсюда 7.7 ГБ
занятой VRAM, подкачка через PCIe и 52 Вт при 100 % утилизации — карта простаивает
на памяти две трети времени, а fidelity 0.00 и ноль шар говорят, что решения не
находятся вовсе.

lolMiner отказывается работать:

```
Device 0: ... Drivers: Cuda     Active: false (Unsupported device or driver version.)
Device 1: ... Drivers: OpenCL   Active: false (OpenCL init failure: Invalid buffer size)
All devices deselected or failed compatiblity check. Closing lolMiner
```

Причина: C32-солверы «mean» требуют 20–33 ГБ VRAM (`grin-miner.toml`:
«the C32 reference miner requires 20GB of memory»; минимум по документации
High-Resource-Cuckatoo-Miner — 24.8 ГБ). В 8 ГБ помещается только lean.

**Следствие для критерия приёмки.** Планка «≥90–95 % от GMiner/lolMiner» на этой
карте сейчас лежит на полу: 0.07 GPS у GMiner и полный отказ lolMiner. Любой
корректно работающий lean-солвер её превышает. Это не повод расслабляться —
реальная цель должна измеряться против физически возможного максимума.

## 2. Верхняя оценка для lean C32 на 4060 Ti

`lean.cu` за один граф делает:

| Операция | Объём на граф |
|---|---|
| `cudaMemset(alive)` один раз | 512 MiB |
| `cudaMemset(nonleaf)` × 128 раундов | **64 GiB** |
| `count_node_deg` — скан `alive` × 128 | 64 GiB |
| `kill_leaf_edges` — скан `alive` × 128 | 64 GiB |
| `cudaMemcpy` bitmaps D→H | 512 MiB |
| CPU popcount по 512 MiB | 512 MiB |
| Построение графа на CPU (adjlist+links) | ~400 MiB записей |

Итого только трафик памяти GPU ≈ **192 GiB на граф**. При эффективной полосе
~250–280 ГБ/с (AD106, 288 ГБ/с пиково) это ≈ **0.7–0.8 с на граф**, то есть
потолок порядка **1.2–1.4 GPS** — и это без учёта siphash-вычислений и скачков
кэша. Реальный lean будет заметно ниже, особенно на CPU-части.

Оценки в открытых источниках для C32 lean на mid-range Ada: 0.1–0.4 GPS.
Собственный замер заменит эту оценку после первого сборка (см. `solver_bench`).

## 3. Фактические измерения собственного солвера

Собрано MSVC 14.51 + CUDA 13.4 (`-arch=sm_89`), задача взята живая с
`grin.2miners.com:3030`. `solver_bench --pre-pow-file build\job.txt`.

| Конфигурация | trim | cycles (CPU) | Рёбер после тримминга | Итог |
|---|---|---|---|---|
| `ntrims=128 blocks=128 tpb=128` | 16.83 с | 0.44 с | 1 026 168 | **0.056 GPS** |
| `ntrims=128 blocks=408 tpb=128` | 16.79 с | 0.50 с | 1 026 168 | 0.056 GPS |
| `ntrims=128 blocks=816 tpb=128` | 16.59 с | 0.44 с | 1 026 168 | 0.057 GPS |
| `ntrims=128 blocks=204 tpb=256` | 16.79 с | 0.44 с | 1 026 168 | 0.057 GPS |
| `ntrims=16` | **14.52 с** | — | 51 601 082 | OVERLOADED |
| `ntrims=96`, `ntrims=32` | — | — | — | не завершились за 10 мин (см. ниже) |

Питание во время работы: **48–77 Вт**, утилизация GPU 100 %, **память 33–54 %**,
температура 48–53 °C, VRAM 3.2 ГБ.

### Что из этого следует

1. **Геометрия запуска не влияет вообще** (16.59–16.83 с при изменении числа
   блоков в 6.4 раза). Значит, дело не в occupancy и не в количестве потоков.
2. **14.5 из 16.8 секунд — это первые ~16 раундов**, где живы почти все
   4.3 млрд рёбер. Оставшиеся 112 раундов стоят всего ~2.2 с. То есть цена
   сосредоточена там, где граф плотный.
3. **Память загружена на 33–54 %**, а не на 100 % → упор не в полосу пропускания,
   а в латентность случайных обращений и в `atomicOr` на битмап `nonleaf`
   (по одному на каждое живое ребро в каждом раунде).
4. **Энергоэффективность пока хуже, чем у сломанного GMiner**: 70 Вт на
   0.056 GPS против 52 Вт на 0.07 GPS. По кредо «хешрейт на ватт» это
   неприемлемо и является главным аргументом за оптимизацию, а не за косметику.
5. **`ntrims` нельзя уменьшать безнаказанно**: при 16 раундах остаётся 51.6 млн
   рёбер — больше `MAXEDGES` (16.7 млн), солвер возвращает `Overloaded`. При 32
   раундах число рёбер оказывается чуть ниже лимита, и CPU-построение графа
   уходит в бесконечность — это отдельный баг, который нужно ограничить
   (см. раздел 5.1).

## 4. План оптимизаций (по убыванию ожидаемого эффекта)

### 4.0 Обязательное: ограничить CPU-поиск циклов

Наблюдалось зависание на `ntrims=32`: число выживших рёбер оказывается чуть ниже
`MAXEDGES`, и `graph::add_edge` с включённой проверкой дублей обходит список
смежности, что при степенях в тысячи даёт квадратичное поведение. В майнере это
выглядит как полная остановка (watchdog видит «нет прогресса», но граф не
прерывается).

Что нужно:

* бюджет времени/итераций на `findcycles` — по превышении возвращать
  `Overloaded` и переходить к следующему nonce;
* не подавать в `findcycles` графы с числом рёбер близким к `MAXEDGES`
  (например, требовать `nedges < MAXEDGES / 4`);
* вынести построение графа в отдельный поток, чтобы watchdog мог его прервать.

### 4.1 Список живых 32-рёберных слов (ожидаемо 3–8× на поздних раундах)

Держать компактный массив индексов слов `alive`, где есть живые рёбра:

* раунд 0: список = все 134 млн слов;
* после каждого раунда — компакция: `kill_leaf_edges` помечает слово как
  «опустевшее», отдельное ядро (или тот же проход) добавляет индексы непустых
  слов в новый список через `atomicAdd` на глобальном счётчике;
* последующие раунды итерируют только по списку.

Побочный эффект: `nonleaf` тоже перестаёт требовать полной очистки — вместо
`cudaMemset` 512 МБ на раунд достаточно сбрасывать только посещённые слова
(их число берётся из того же списка). Это убирает ещё и 64 GiB memset.

Ожидаемый итог: трафик падает с ~192 GiB до ~20–30 GiB на граф.

### 4.2 Отказ от полного `cudaMemset(nonleaf)` (ожидаемо 1.3–1.5×)

Уже входит в 4.1, но полезно и само по себе. Альтернатива без списка: хранить
номера посещённых слов и чистить только их.

### 4.3 Геометрия запуска (ожидаемо 1.1–1.3×)

`blocks=128, tpb=128` = 16 384 потоков на 134 млн слов, то есть 8192 итерации на
поток. Для latency-bound нагрузки нужен больший параллелизм: пробовать
`blocks` 512–4096 при `tpb` 128–256. Скрипт замера уже параметризован
(`solver_bench --blocks --tpb`).

### 4.4 `PART_BITS` (память ↔ скорость)

`PART_BITS=1` вдвое уменьшает `nonleaf` (256 МБ) ценой ~33 % замедления по
документации Tromp. На 8 ГБ память не является ограничением (нужно ~1 ГБ), так
что `PART_BITS=0` — правильный выбор. Опция оставлена для карт с малым VRAM.

### 4.5 Подбор `ntrims` (ожидаемо 1.2–2×)

`ntrims=128` — значение по умолчанию Tromp для `EDGEBITS=31`. Для `EDGEBITS=32`
стартовое число рёбер вдвое больше, и upstream **никогда не собирал C32**
(в Makefile есть `lcuda19/29/30/31`, но нет `lcuda32`). Поэтому 128 — не
оттюненное значение, а перенос.

Опасность в обе стороны:

* мало раундов → после тримминга остаётся больше `MAXEDGES = 2^24 = 16.7 млн`
  рёбер → солвер возвращает `Overloaded` и граф пропадает (upstream в этой
  ситуации вызывал `exit(0)`; у нас — статус, см. `CH-4`);
* много раундов → лишняя работа.

`solver_bench` печатает `edges=...` после каждого графа, поэтому оптимум
подбирается одним прогоном без пересборки: `--ntrims` 96/128/160/192.

## 5. Что мерить в первую очередь

```bat
solver_bench.exe --selftest
solver_bench.exe --pre-pow-file build\job.txt --seconds 60
solver_bench.exe --pre-pow-file build\job.txt --nonce-count 5 --ntrims 96
solver_bench.exe --pre-pow-file build\job.txt --nonce-count 5 --blocks 1024
```

Порядок работ: сначала **корректность** (все решения проходят `grin_verify` и
принимаются пулом), затем 4.1/4.2, затем 4.3/4.5. Оптимизировать солвер, который
не находит валидных циклов, бессмысленно.

## 6. Прочая экономика

Сеть GRIN ~3.5–4 kGps, её добывают ASIC (iPollo G1: 36 h/s при 2800 Вт). Одна
4060 Ti даёт 0.01–0.02 % сети. Выручка по WhatToMine — порядка $0.16/сутки при
убытке $0.13 при $0.13/кВт·ч. Проект имеет смысл как инженерный, как
измерительный стенд и как заявка на bounty Tromp ($10 000 за открытый
C32-солвер на 1 gps при ≤100·x Вт): 4060 Ti при ~100 Вт должна дать ~1 GPS,
то есть цель — ровно наш потолок из раздела 2.
