# Разбор: почему солвер долго не находил решения

Документ переписан после того, как независимая проверка опровергла первую версию
диагноза. Ниже — только то, что подтверждено измерениями.

## Итог

**Пайплайн корректен.** Тримминг проверен против независимого вычисления 2-ядра,
поиск циклов — обычный двудольный обход без трюков. Решения на C32 редки
(оценочно ~2 % на граф), поэтому «ноль решений за 24 графа» ничего не доказывал.

## Что подтверждено измерениями

| Утверждение | Как проверено | Результат |
|---|---|---|
| Заголовок → ключи siphash | независимый BLAKE2b (`hashlib`) и независимый siphash на Python | совпадают с C++ побитово |
| device- и host-siphash | `solver_bench --device-check` (C32) | 0 расхождений из 64 |
| **Тримминг сходится к истинному 2-ядру** | `tools/ref_core.py` — независимый Python-расчёт 2-ядра (удаление вершин степени 1) | при `ntrims=256` GPU даёт **488** рёбер, Python даёт **488** рёбер |
| Тримминг монотонен по раундам | `--ntrims` 32/64/128/256 на C20 | 3935 → 1226 → 581 → 488 |
| Тримминг сохраняет циклы | удаляются только листья; сходимость к 2-ядру подтверждена выше | циклы не теряются |
| Поиск циклов | `src/solver/cycle_finder.hpp` — двудольный CSR-граф, обход в глубину, без `^1` | работает; ограничен бюджетом шагов |

## Ошибка первой версии диагноза

Ранее здесь утверждалось, что `graph.hpp::add_edge` несовместим с моделью
Cuckatoo и поэтому циклы не находятся. Это **не подтвердилось**:

* ключевое наблюдение «`raw_cycles = 0`» было получено на параметрах
  `EDGEBITS=20 / PROOFSIZE=6`;
* независимый расчёт показал, что при 2^20 рёбер истинное 2-ядро состоит из
  **487 узлов и 488 рёбер** и представляет собой практически одну длинную петлю —
  коротких циклов там **не существует**;
* следовательно, ноль 6-циклов на C20 — правильный ответ, а не признак ошибки.

Дополнительно 20 000 графов на C20/P6 дали ровно ноль решений — что для графа без
6-циклов и должно быть.

## Сколько решений ожидать на C32

Оценка из параметров сети GRIN (октябрь 2026):

* сеть ~3.5 kGps, блок раз в 60 с ⇒ ~210 000 графов на блок;
* сложность сети требует примерно 12 ведущих нулей в cyclehash ⇒ 1/4096;
* отсюда вероятность хотя бы одного 42-цикла на граф ≈ 4096 / 210 000 ≈ **2 %**.

Значит:

| Число графов | Вероятность не увидеть ни одного решения при p=2 % |
|---|---|
| 24 | 61 % |
| 100 | 13 % |
| 300 | 0.2 % |

Наблюдаемые нули (24 графа на C32, 300 на C29) **согласуются** с этой оценкой:
на C29 ядро беднее, и вероятность там ещё ниже.

## Что было исправлено по дороге (и почему это не зря)

1. **`cycle_finder.hpp`** — замена финальной стадии на явный двудольный граф:
   плотные индексы узлов через хеш-таблицу, CSR-смежность, обход в глубину с
   **жёстким лимитом шагов**. Прежний рекурсивный DFS без лимита вешал прогон
   более чем на 10 минут, а таблица компрессора `compress.hpp` при малом `ntrims`
   переполнялась и молча возвращала мусорные идентификаторы (`NODE OVERFLOW`).
   Теперь переполнение — это чистый статус `Overloaded`, а не порча графа.
2. **CH-7**, тест листа через 2-битный счётчик степени вместо однобитного
   битмапа. Сходимость к истинному 2-ядру (488 = 488) подтверждает, что тримминг
   теперь считает степень корректно.
3. **Host-интеграция**: считался фиктивный хешрейт (6440 GPS при 0 % GPU), список
   пулов дублировался, до прихода первой задачи шёл холостой цикл на
   ненастроенном солвере. Исправлено, проверено на живом пуле.

## Как проверять дальше

Единственный оставшийся вопрос — фактическая частота решений на C32. Правильный
тест — длинный прогон:

```bat
solver_bench.exe --pre-pow-file build\job.txt --nonce-count 400
```

Ожидание при p≈2 %: ~8 решений за 400 графов (около 2 часов). Каждое решение
обязано пройти `grin_verify` (это делает сам бенчмарк) и затем быть принято пулом.

Промежуточные инструменты, которые уже отлажены и которыми нужно пользоваться
перед любыми выводами:

* `tools/ref_core.py` — независимый Python-эталон 2-ядра; сравнивать с
  `solver_bench_tiny` при `--ntrims 256`;
* `solver_bench --device-check` — согласованность device/host siphash;
* `selftest` — KAT BLAKE2b и раскладка заголовка;
* `raw_cycles` / `verify_failures` в отчётности — различают «поиск не нашёл» и
  «индексы распакованы неверно».

**Урок:** параметры проверки надо выбирать там, где решения заведомо существуют.
`EDGEBITS=20` с `PROOFSIZE=6` к таким не относится, и отрицательный результат на
них не означает ошибку.
