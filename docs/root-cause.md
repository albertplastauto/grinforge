# Почему солвер не находит решения: разбор и доказательства

Статус: **блокер найден, исправление не внесено.** Майнер собирается, корректно
триммит граф и общается с пулом, но **не находит ни одного цикла** — и поэтому не
отправляет ни одной шары.

## Что доказано и чем

| Утверждение | Доказательство |
|---|---|
| Заголовок → ключи siphash верны | `tools/check_keys.py` (независимый BLAKE2b из Python) совпадает с C++ на 4 nonce; `tools/check_siphash.py` (независимый siphash на Python) совпадает с C++ |
| device- и host-siphash согласованы | `solver_bench --device-check` (C32): **0 расхождений из 64** |
| Тримминг корректен | Размер 2-ядра совпадает с теорией `n^(2/3)`: C20 теория ~10–13K, наблюдаем **13 533**; C29 теория ~660K, наблюдаем **427K**; C32 теория ~2.6M, наблюдаем **1.0M** |
| Число раундов достаточно | 128 раундов дают стабильные ~1.0M рёбер на C32, перегрузки нет |
| **Поиск циклов не работает** | `raw_cycles=0` и **ни одной строки `cycle found`** за все прогоны |

Ключевой эксперимент — тот же конвейер на крошечных параметрах
(`EDGEBITS=20`, `PROOFSIZE=6`, 2-ядро ~13 000 рёбер, `solver_bench_tiny`):
циклы длины 6 в таком графе обязаны быть (оценка ~5–25 на граф), но не найдено
**ни одного**, и `print_log("  %d-cycle found\n", len)` не сработал ни разу.

## Где именно ломается

Финальная стадия `lean.cu`:

```cpp
word_t u = sipnode(&sipkeys, nonce, 0), v = sipnode(&sipkeys, nonce, 1);
cg.add_compress_edge(u, v);          // -> add_edge(compressu->compress(u), compressv->compress(v))
```

`graph.hpp::add_edge` замыкает цикл только при условии:

```cpp
if (adjlist[u ^ 1] != NIL && adjlist[v ^ 1] != NIL) { ... cycles_with_link(...); }
```

Это условие предполагает, что **партнёр узла `u` — это узел `u ^ 1`**, то есть что
узлы идут парами (2i, 2i+1). В модели Cuckatoo это не так: `sipnode` возвращает
`blake2b`-хеш под маской, без бита партиции:

```cpp
word_t sipnode(siphash_keys *keys, word_t edge, u32 uorv) {
  return keys->siphash24(2*(u64)edge + uorv) & NODEMASK;
}
```

Партиция закодирована во **входе** хеша (`2*edge + uorv`), а не в выходе. Поэтому у
узла нет «партнёра» `u ^ 1`.

`compress.hpp` усугубляет: младший бит сжатого идентификатора берётся из
**случайного младшего бита исходного хеша**, а не из партиции:

```cpp
u32 parity = u & 1;
...
return (npairs++ << 1) | parity;
```

Значит `compressed_u ^ 1` — это, как правило, вообще несуществующий слот, и
`adjlist[u ^ 1]` остаётся `NIL`. Условие замыкания не выполняется → цикл не
регистрируется никогда.

Побочное подтверждение: в одном из ранних прогонов на C32 всё же появились
строки `2-cycle found` и `22-cycle found` — то есть условие *может* сработать при
совпадении, но это случайность, а не систематический обход графа.

## Почему это не поймали раньше (и почему смогли поймать сейчас)

* Тримминг честно уменьшает граф: 4.29 млрд рёбер → ~1 млн. Внешне всё
  выглядит работающим, и ошибка не проявляется до самого поиска циклов.
* Штатный путь Tromp для Cuckatoo (`src/cuckatoo/lean.cu`) **никогда не
  собирался**: в `Makefile` есть `lcuda19/29/30/31`, но нет `lcuda32`. Живой
  сборки, на которой этот код кто-то проверял бы в бою, не существует.
* Отрицательный результат легко списать на «решения редки»: 0 из 24 графов на
  C32 выглядит правдоподобно. Именно поэтому понадобился запуск на
  `EDGEBITS=20/PROOFSIZE=6`, где вероятность решения высокая.

## Что делать (следующий шаг)

Заменить финальную стадию на поиск циклов, корректный для модели Cuckatoo:

1. Строить **двудольный** граф без трюка `^1`: узлы партиции 0 — `[0, MAXNODES)`,
   партиции 1 — `[MAXNODES, 2*MAXNODES)`, как это уже делает `add_edge` строкой
   `v += MAXNODES`.
2. Обходить граф от обоих концов ребра, замыкая цикл, когда достигнут исходный
   узел, и искать путь длины ровно `PROOFSIZE`.
3. Валидировать на `EDGEBITS=20/PROOFSIZE=6` (должны появиться решения и
   проходить `grin_verify`), затем на `EDGEBITS=29/PROOFSIZE=42`, и только потом
   на C32.
4. Держать `raw_cycles` в отчётности: `raw_cycles > 0` при `solved == 0` означает
   ошибку в распаковке индексов, `raw_cycles == 0` — ошибку в самом поиске.

Инструменты для проверки уже готовы и отлажены:
`solver_bench_tiny` (C20/P6), `solver_bench29` (C29), `solver_bench` (C32),
`solver_bench --device-check`, `selftest`, `check_keys.py`, `check_siphash.py`.

## Отдельно: ограничить время поиска циклов

Наблюдалось зависание на `ntrims=32`: `graph::add_edge` с проверкой дублей обходит
список смежности, что при больших степенях даёт квадратичное поведение, а
рекурсивный DFS `cycles_with_link` не имеет ограничения по числу шагов. В майнере
это выглядит как полная остановка. Нужен бюджет итераций/времени и переиспускание
графа в отдельный прерываемый поток.
